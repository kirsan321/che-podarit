## 2. Что нужно сделать — MVP на месяц

Принцип отсечения: в v1 только то, без чего сценарий «получатель собрал список → даритель выбрал и забронировал» не работает.

### MUST (без этого нет продукта)
1. Авторизация получателя (email-код), профиль (имя, фото).
2. Один вечный список: добавить вручную / по ссылке, редактировать, удалить, приоритет, «видно дарителям» / «только я», тип «именно это» vs «направление» (диапазон цены, теги, анти-теги).
3. Парсер ссылок на сервере: WB-адаптер (JSON API) + общий Open Graph + ручной фолбэк (никогда не блокируем добавление).
4. Шеринг: токен-ссылка (≥128 бит), отзыв/перегенерация, QR, публичная страница без регистрации, `noindex`.
5. Даритель (без регистрации, по ссылке): повод + дата + бюджет → колода (свайп) → шорт-лист → выбор → **бронь**. Забронированное скрыто от других дарителей.
6. Режим «сюрприз»: получатель бронь не видит по умолчанию; переключатель «показывать бронь» (только факт, без имени).
7. Пометка «получил» → в историю; автоснятие брони через N дней после даты повода.
8. PWA: манифест, установка, `Web Share Target` (из WB/Ozon «Поделиться → чЁ подарить»).

### SHOULD (делаем в неделю 3, если MUST закрыт по графику)
9. Добавление по фото: сжатие на клиенте → Claude vision → поиск кандидатов в WB → «Это оно?».
10. Рулетка «Довериться удаче» (в макете уже есть, переносится дёшево).
11. «Дарю»: список моих людей/поводов с обратным отсчётом (экран 1 макета дарителя).

### CUT из v1 (в план не входит)
Ozon/Яндекс Маркет как надёжные адаптеры (только best-effort + фолбэк) · импорт избранного целиком · складчина «скинемся» · каталог и рекомендации · уведомления/пуши · публичный профиль и поиск · история «от кого» · пересчёт цен · монетизация.

## 3. Стек (предложение)

| Слой | Выбор | Почему |
|---|---|---|
| Фронт + API | **Next.js 15 (App Router, TypeScript)** | Один репо, SSR для публичной страницы (NFR «< 2 с»), route handlers для парсера/vision (обход CORS), PWA из коробки через `next-pwa`/manifest |
| БД / Auth / Storage | **Supabase** (новый отдельный проект) | Postgres + RLS + email OTP + Storage для фото. Опыт есть. НЕ использовать торговую базу `zpoxspsiuoqkgkailbsr` |
| UI | Tailwind + свои компоненты по макетам | Макеты уже на CSS-переменных, переносятся 1:1 |
| Vision | Claude API (`claude-sonnet-5`) | Спека прямо называет Claude; JSON `{brand, product, variant, confidence}` |
| Хостинг | Vercel (preview на каждый PR) | Ноль DevOps в месячном проекте. ⚠️ Vercel-регион не РФ — парсер маркетплейсов может упереться в гео (см. риски) |
| Аналитика | PostHog (free) | События из NFR: доля списков ≥3, доля по ссылке vs вручную, успех парсинга, доля с бронью |

Альтернатива хостинга парсера, если гео подтвердится: маленький Node-сервис на РФ VPS или РФ-прокси только для `/api/parse-link` и `/api/recognize-photo`.

## 4. Решения по 8 открытым вопросам спеки (предлагаемые дефолты)

| # | Вопрос | Предлагаю для v1 |
|---|---|---|
| 1 | Один список или под поводы | **Один вечный** + необязательные теги поводов на подарке |
| 2 | Минимальная авторизация | **Email + 6-значный код** (Supabase OTP). Телефон/SMS — позже (нужен РФ SMS-провайдер, договор, деньги) |
| 3 | Показывать бронь получателю | **Нет по умолчанию**, переключатель в настройках списка |
| 4 | Снятие брони | **14 дней** после даты повода, если даритель не нажал «подарил» |
| 5 | Каталог в колоду | **Нет.** Короткий список → сообщение «попросите добавить желаний» |
| 6 | Публичный профиль / поиск | **Нет.** Только по ссылке |
| 7 | Импорт избранного WB/Ozon | **Нет** — легального API нет. Share-sheet закрывает 80% сценария |
| 8 | Поиск кандидатов по фото | **WB search API** (бесплатно, без ключа). Ozon/ЯМ — нет |

Эти дефолты не блокируют старт: если партнёр решит иначе — правки локальные.

## 8. Правила совместной работы (предложение, 2026-09-15)
- `main` защищён: пуш только через PR с зелёным CI. Approve не обязателен (решение владельца 2026-09-15), ревью по желанию. Прямые пуши и force-push в `main` запрещены обоим.
- Ветки `feat/<кратко>`, `fix/<кратко>`; один PR = одна задача, живёт не дольше 2 дней, чтобы не копить конфликты.
- Разделение зон на неделю 1–2, чтобы не толкаться в одних файлах: один ведёт роль «Получатель» (список, добавление, шеринг), второй — «Даритель» (события, колода, бронь). Общее (схема БД, auth, дизайн-система) — делаем первым и вместе в первые 2 дня.
- Задачи — GitHub Issues с милстоунами W1–W4 из плана; доска Projects по желанию.
- Supabase: один проект, оба владельцы; миграции только через файлы в репо (`supabase/migrations`), никакого ручного DDL в дашборде.
- Секреты: `.env.local` не в репо, шаблон `.env.example` в репо.
