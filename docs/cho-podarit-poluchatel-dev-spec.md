# «Чё подарить» — документ по разработке: роль «Получатель»

Статус: черновик · Дата: 2026-09-03 · Платформа: адаптивный веб (mobile-first, PWA), без нативных клиентов

> Документ описывает всё, что относится к пользователю в роли **Получателя** — человека, которому дарят. Роль «Даритель» описана в отдельном документе (`cho-podarit-daritel-dev-spec.md`). Пометка «(уточнить)» — гипотеза, требующая решения.

## 1. Роль и цель

Получатель — не обязательно именинник. Это любой человек, у которого есть **готовый список желаний**, и повод может быть любой: день рождения, Новый год, свадьба, новоселье, «просто так», «спасибо за помощь». Цель роли — один раз собрать и поддерживать актуальный список, чтобы дарители выбирали из него, а не гадали. Побочная цель — не получать дубли и ненужное.

## 2. Целевая аудитория

**Ядро:** женщины 25–45 лет, регионы, активные покупатели маркетплейсов. По открытым данным (Mediascope, портреты покупателей WB/Ozon/Авито за 2025): основная аудитория российских маркетплейсов — женщины 25–44 из регионов; у Wildberries женщин ~60–70%, у Ozon ~55%; около 60% покупок — спонтанные и импульсивные.

**Что это значит для продукта:**
- У пользователя **уже есть** избранное и корзина на WB/Ozon. Список желаний не должен собираться с нуля — он должен *переноситься* оттуда (см. раздел 6.2).
- Пользователь привык к UI/UX маркетплейсов: карточки товара, поиск, фильтры, избранное «сердечком». Наш интерфейс должен ощущаться так же привычно, а не как «ещё одно приложение, которое надо изучать» (см. раздел 6.6).
- Время в маркетплейсах — минуты в день, не часы (точных свежих цифр по времени в приложении в открытых источниках нет). Значит, сценарии должны быть короткими: добавить подарок — одно действие, поделиться списком — одно действие.

## 3. Связь с ролью «Даритель»

Список получателя — это **источник колоды** для свайпов дарителя. Даритель свайпает не абстрактный каталог, а то, что получатель реально хочет, отфильтрованное под бюджет дарителя. Отсюда главные требования к получателю: список должен быть простым в наполнении, всегда актуальным и доступным по ссылке без регистрации для дарителя.

## 4. Путь Получателя (end-to-end)

1. **Вход.** Открывает приложение (ссылка, QR, PWA). Для создания списка нужна авторизация (уточнить: минимально — телефон/email/соцсеть), иначе список нельзя будет редактировать с другого устройства.
2. **Создание списка.** Один «вечный» список желаний по умолчанию; опционально — списки под повод (уточнить: нужны ли отдельные списки в v1 или достаточно одного с тегами поводов).
3. **Наполнение.** Добавление подарка: вставить ссылку на товар (парсим название, фото, цену), выбрать из каталога приложения, или создать вручную (название, примерная цена, фото, комментарий «размер M», «любой цвет кроме красного»).
4. **Приоритеты и настройки.** Пометить «очень хочу» / «было бы приятно»; указать, можно ли скидываться на дорогое (уточнить, v1 или позже).
5. **Шеринг.** Получатель делится ссылкой/QR/кодом. Дарителю открывается список без регистрации.
6. **Обратная связь.** Получатель видит, что кто-то «забронировал» подарок (без деталей кто и какой — чтобы сохранить сюрприз), либо вообще ничего не видит (уточнить режим, см. раздел 7).
7. **После события.** Пометить «получил», убрать из списка; полученное уходит в историю. Список живёт дальше до следующего повода.

## 5. Экраны и модули

| Модуль | Экраны | Приоритет |
|--------|--------|-----------|
| Авторизация | Вход/регистрация, профиль (имя, фото, дата рождения — опц.) | must |
| Список желаний | Список, добавление (по ссылке / из каталога / вручную), редактирование, приоритет, удаление | must |
| Импорт из маркетплейсов | Вставка ссылки WB/Ozon/ЯМаркет с надёжным парсингом; share-sheet «Поделиться → Чё подарить» (PWA Web Share Target) | must |
| Парсер ссылок | Извлечение названия/фото/цены с любой страницы товара (Open Graph + фолбэк) | must |
| Добавление по фото | Снимок → vision-модель распознаёт бренд/название → поиск на маркетплейсах → подтверждение совпадения | must |
| Шеринг | Ссылка, QR, короткий код; настройки приватности | must |
| Бронирование | Показ/скрытие статуса «кто-то выбрал» | should |
| История | Полученные подарки, от кого (если даритель раскрылся) | could |
| Уведомления | «Кто-то открыл ваш список», напоминание обновить список перед поводом | could |

## 6. Ключевые сценарии и правила

### 6.1 Список без привязки к поводу
- Список существует постоянно, а не создаётся под событие. Повод задаёт **даритель** на своей стороне (событие + бюджет), список получателя от этого не меняется.
- Опциональные теги поводов на подарке («на НГ», «на ДР») — фильтр для дарителя, не обязательны (уточнить).

### 6.2 Добавление по ссылке и импорт из маркетплейсов
- **Приоритет парсинга:** Wildberries, Ozon, Яндекс Маркет — отдельные адаптеры с извлечением названия, фото, цены и вариантов (размер/цвет), покрытие тестами; остальные сайты — общий парсер по Open Graph.
- **Share-sheet:** приложение регистрируется как Web Share Target (PWA), чтобы из приложения WB/Ozon можно было нажать «Поделиться» → «Чё подарить» и товар сразу попал в список. Это основной сценарий добавления для целевой аудитории.
- **Импорт избранного целиком** — could; зависит от наличия легального способа (открытого API/экспорта у площадок нет — уточнить).
- Общий путь: пользователь вставляет URL → сервер тянет страницу, берёт `og:title`, `og:image`, цену (по мета-тегам или эвристике по площадкам).
- Если парсинг не удался — форма с предзаполненным URL, остальное вручную. Никогда не блокируем добавление из-за неудачного парсинга.
- Цена хранится как «ориентир на дату добавления», с пометкой; пересчитывать автоматически — could.

### 6.3 Добавление по фото (распознавание vision-моделью)
Сценарий: пользователь в магазине фотографирует товар (духи, кроссовки, книгу) — желание появляется в списке с названием и ценой, без ввода текста.

**Поток:**
1. Тап по камере в поле добавления → снимок (или выбор из галереи, в т.ч. скриншот сторис).
2. Фото сразу сохраняется как карточка-заглушка с этим фото (optimistic UI, скелетон вместо названия).
3. Снимок уходит на сервер → vision-модель (Claude / аналог) возвращает JSON: `{brand, product, variant, category, confidence}`. Промпт просит читать текст с упаковки и не додумывать.
4. По `brand + product` — поиск на WB/Ozon/ЯМаркет, 1–3 кандидата с фото и ценой.
5. Пользователю показывается «Это оно?» с кандидатами; тап — карточка дозаполняется (название, цена, ссылка, фото с площадки заменяет снимок либо остаётся рядом). «Ничего из этого» — остаётся фото + название от модели, редактируется вручную.

**Требования:**
- Время до результата ≤ 5 с; всё это время карточка уже в списке, пользователь может уйти с экрана.
- При `confidence` ниже порога кандидатов не показываем — только предзаполненное название с пометкой «проверь».
- Обработка на сервере; фото сжимается на клиенте до ~1024 px перед отправкой.
- Приватность: фото не используется для обучения, удаляется после распознавания, если пользователь не оставил его как картинку желания; в UI — короткое пояснение при первом использовании.
- Стоимость: копейки за запрос; лимит на пользователя в день от злоупотреблений (уточнить число).
- Аналитика: доля добавлений по фото, доля подтверждённых кандидатов, доля ручных правок после распознавания.

**Не делаем:** сканер штрихкодов и «просто фото без распознавания» как отдельные режимы — распознавание покрывает оба сценария.

### 6.4 Приватность
- Список открывается **только по ссылке/коду**, в поиске приложения его нет (уточнить: нужен ли публичный профиль).
- Ссылку можно отозвать и сгенерировать новую.
- Отдельные подарки можно скрыть от конкретного списка/ссылки (например, «это не для коллег») — could.

### 6.5 Дубли
- Когда даритель выбрал подарок (финал в своём сценарии), подарок помечается как **забронированный** для других дарителей: в колоде он больше не показывается.
- Бронь снимается автоматически через N дней после даты события, если даритель не подтвердил «подарил» (уточнить N).

### 6.6 UI/UX: ориентир — привычки маркетплейсов
Цель — чтобы пользователь WB/Ozon чувствовал себя «дома» с первого экрана. Конкретные требования:
- **Карточка подарка = карточка товара:** крупное фото, название, цена, «сердечко»/чекбокс. Те же пропорции и порядок элементов, что в лентах маркетплейсов; сетка 2 в ряд на мобильном.
- **Список желаний ведёт себя как «Избранное»:** добавить — одно касание, убрать — одно касание, без диалогов подтверждения (с undo-тостом).
- **Добавление по ссылке — как вставка в поиск:** одно поле сверху, вставил ссылку → карточка появилась. Заполнение вручную — только если парсинг не сработал.
- **Нижняя навигация** (3–4 пункта: Список, Поделиться, Подарки/История, Профиль) — как у всех маркетплейсов, не бургер-меню.
- **Скелетоны вместо спиннеров**, бесконечная лента вместо пагинации, pull-to-refresh.
- **Нулевое обучение:** никаких туториалов на 5 экранов; максимум одна подсказка на пустом списке «Вставь ссылку с WB или Ozon».
- **Ожидаемые скорости:** первый экран < 2 с на мобильной сети, отклик на тап < 100 мс.
- **Тексты** — короткие, в разговорном тоне маркетплейсов: «Добавить», «Хочу», «Поделиться списком», без канцелярита.
- **Не копировать вслепую:** маркетплейсы перегружены акциями, баннерами и таймерами — этого у нас быть не должно. Берём привычные паттерны навигации и карточек, не берём агрессивный маркетинг.

**Проверка:** перед релизом — usability-тест с 5–6 женщинами 25–45, которые регулярно покупают на WB/Ozon: задача «добавь три подарка из своего избранного на WB и отправь список подруге» без подсказок, целевое время — до 2 минут.

## 7. Режим «сюрприз»

Решение продукта: **получатель по умолчанию не видит, какие подарки забронированы** — иначе теряется сюрприз. Настройка «показывать бронь» включается самим получателем (для тех, кому важнее не получить дубль, чем сюрприз). Даже при включённом режиме показывается только факт «забронировано», без имени дарителя, пока даритель сам не раскроется после вручения.

## 8. Данные и API (черновик)

**Сущности:** `User`, `Wishlist` (один или несколько на пользователя), `WishItem` (название, url, фото, цена-ориентир, приоритет, комментарий, теги поводов, статус: `active` / `reserved` / `received`), `ShareLink` (токен, срок, отозвана/нет), `Reservation` (ссылка на `Event` дарителя).

**Эндпоинты:**
- `POST /api/wishlists`, `GET /api/wishlists/:id`, `PATCH /api/wishlists/:id`
- `POST /api/wishlists/:id/items` — `{url?}` или ручные поля; `PATCH`/`DELETE /api/items/:id`
- `POST /api/parse-link` → `{title, image, price, currency}` — с таймаутом и фолбэком
- `POST /api/recognize-photo` (multipart) → `{brand, product, variant, confidence, candidates: [{title, image, price, url, source}]}`
- `POST /api/wishlists/:id/share` → `{token, url, qr}`; `DELETE /api/share/:token` — отзыв
- `GET /api/public/wishlists/:token` — для дарителя, без авторизации; `reserved` отдаётся дарителям, получателю — по настройке
- `POST /api/items/:id/received`

**Связь с Дарителем:** `GET /api/deck?event_id=…` на стороне дарителя строит колоду из `WishItem` со статусом `active` и ценой ≤ бюджета (+ каталожные предложения, если список короткий — уточнить).

## 9. Нефункциональные требования

- Добавление подарка по ссылке — до 3 с с показом скелетона; парсинг на сервере, чтобы обходить CORS. Адаптеры WB/Ozon/ЯМаркет мониторятся: при падении доли успешного парсинга ниже 90% — алерт.
- Публичная ссылка открывается без регистрации и быстро (SSR или статика для первого экрана — should).
- Приватность: списки не индексируются (`noindex`), токен ссылки не угадывается (≥ 128 бит).
- PWA: установка на домашний экран, пуши о брони (если включён режим) — could.
- Аналитика: доля списков с ≥ 3 подарков, доля добавлений по ссылке vs вручную, доля успешного парсинга, доля списков, по которым была хотя бы одна бронь.

## 10. Вне рамок документа

## 11. Открытые вопросы

1. Один «вечный» список или отдельные списки под поводы в v1?
2. Минимальная авторизация — телефон, email или соцсеть?
3. Показывать ли получателю бронь по умолчанию (сейчас — нет, включается вручную)?
4. Через сколько дней снимать неподтверждённую бронь?
5. Дополнять ли короткий список получателя каталожными предложениями в колоде дарителя?
6. Нужен ли публичный профиль / поиск получателей по имени?
7. Есть ли легальный способ импортировать избранное WB/Ozon целиком?
8. Поиск кандидатов по распознанному названию — через какой источник: собственный парсинг выдачи площадок, партнёрские API или общий веб-поиск?
